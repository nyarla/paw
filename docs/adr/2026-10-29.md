# ADR 2026-10-29: PAW audio wire の初期設計とアーキテクチャ決定

- Status: Accepted
- Date: 2026-10-29
- Scope: プロジェクト初期設計（実装前）
- 関連: `docs/design.md`, `docs/protocol.md`, `docs/roadmap.md`, `docs/limitations.md`

## 1. 背景

LAN 内で VST / CLAP プラグインを共有するソフトウェアを Rust で作る。特に、Wine prefix 内の Windows 向けプラグインを Linux DAW から利用できることを重視する。

当初は「プラグイン共有」の意味が複数あり得たため、以下の解釈を整理した。

- リモート処理（プラグインは Host 側で動作し、音声だけをネットワーク転送する）
- バイナリ / プリセットの配布・同期
- セッション / プリセット構成の共有
- P2P でのプラグイン実体の共有

本プロジェクトでは **リモート処理** を採用する。プラグインのバイナリを配布するのではなく、各ユーザーの環境にあるプラグインを Host がロードし、Client が DAW から見えるプラグインとして音声を中継する。

## 3. システム構成

```text
DAW
 └─ Client (CLAP / 将来 VST3)
      ├─ control TCP -> Supervisor
      └─ audio UDP   -> Worker（session.create で返された endpoint）

Supervisor (pawd、1 prefix に 1 つ)
 ├─ control TCP server
 ├─ catalog / allowlist
 ├─ session registry
 ├─ worker manager
 │    ├─ Worker: vendor A (pawd --worker)
 │    │    ├─ plugin instance 1
 │    │    └─ plugin instance 2
 │    └─ Worker: vendor B
 │         └─ plugin instance 3
 └─ endpoint file / pawd.lock
```

## 4. プロセスモデル

### 4.1 「1 prefix 1 host」の意味

1 prefix（または 1 native instance）につき **Supervisor 1 + vendor worker N** とする。Supervisor はプラグインを直接ロードせず、カタログ管理・セッション管理・Worker の起動を行う。

### 4.2 ベンダーごとの Worker 分離

- 同一ベンダーのプラグインは同一 Worker プロセスにロードする
- 異なるベンダーは別 Worker に分離する
- 同一ベンダーのプラグイン同士で、プロセス内グローバル / Windows の名前付き共有メモリ / 名前付きパイプによる IPC が成立する
- 異なるベンダー間のクラッシュやグローバル状態の衝突を隔離できる

共有メモリ要件は **プラグイン同士の IPC** と定義する。Client と Host の音声バッファを共有メモリにする要件は、MVP では対象外とする。

### 4.3 トレードオフ

- 同一 Worker 内の 1 プラグインがクラッシュすると、その Worker の全セッションが失われる
- ベンダー単位の分離であり、セッション単位の完全なサンドボックスではない
- Worker クラッシュ時は Supervisor が検知し、該当ベンダーのセッションだけ `session.lost` にする
- Client はキャッシュした state でセッションを再作成する
- Supervisor が落ちた場合、Worker は control 切断を検知して終了する

### 4.4 検討した代替案

- **全セッションを 1 プロセスに集約**: 実装は単純だが、クラッシュ分離がなく、ベンダー間のグローバル状態も混ざる。却下。
- **セッションごとにプロセス分離**: 安全性は高いが、同一ベンダーの IPC が成立せず、プロセス数・メモリ・起動コストも増える。MVP では却下。
- **ベンダーごとの分離**: 上記の中間。ベンダー IPC とクラッシュ分離を両立できるため採用。

## 5. 起動とライフサイクル

### 5.1 共通起動フェーズ

Runtime が native でも Wine でも、同じフェーズを使う。

```text
1. resolve_runtime
2. compute_endpoint_key
3. try_connect
4. acquire_spawn_lock
5. recheck
6. spawn
7. await_ready
8. release_lock
9. supervise
```

- `endpoint_key` は `runtime種別 + prefix + pawd exe + protocol major + user` のハッシュ
- spawn 競合は native 側のファイルロックで直列化する
- Supervisor 自身も `pawd.lock` を取り、二重起動を防ぐ
- endpoint は control server の bind 後に原子的に書き、`hello` 成功で ready とする
- 起動失敗時は Host の stdout / stderr をログに残す

### 5.2 Runtime ごとの差分

| Runtime | spawn | endpoint / lock | パス変換 |
|---|---|---|---|
| Linux native | `pawd serve ...` | `$XDG_RUNTIME_DIR/paw/<key>.json` | なし |
| Wine (Linux) | `WINEPREFIX=... wine pawd.exe serve ...` | native path を `Z:\...` で Supervisor に渡す | native ↔ Windows |

macOS native / macOS Wine は現時点では対象外。起動フェーズは Runtime を差し替えて追加できる形にしておく。

### 5.3 自動起動

- DAW のプラグインスキャン時には起動しない
- `activate` をトリガーに非同期で起動する
- `activate` 自体はブロックしない。起動完了までは無音を返す
- `start_processing` / 初回 `process` をフォールバックトリガーにする
- 緊急時は `PAW_DISABLE_AUTOSTART=1` で無効化できる

```toml
[host]
autostart = "on_activate"   # on_activate | on_start_processing | manual
```

### 5.4 Worker のライフサイクル

- 最初のセッション作成時に Supervisor が `pawd --worker` を spawn する
- Worker は control 接続で Supervisor に `worker.hello` を送る
- セッションが `worker_idle_sec` の間 0 なら Worker は終了する
- Worker が落ちた場合、Supervisor は該当ベンダーのセッションだけ `session.lost` にする

## 6. プラグインカタログとベンダーグループ

### 6.1 カタログ

Supervisor はプラグインを scan し、カタログとして保持する。Client はプラグインのパスを送らず、カタログ ID を送る。Supervisor が allowlist とカタログから解決する。

`PluginMetadata` の主な項目:

- `format`: `clap` / `vst3` / `vst2`
- `id`: CLAP plugin id、VST3 class id、VST2 unique id
- `name`
- `vendor_raw`: プラグイン由来のベンダー文字列
- `vendor_key`: 正規化したベンダーキー
- `group`: 実際に使用する Worker グループ
- `group_source`: `config` / `alias` / `vendor` / `id` / `path` / `default`
- `kind`: `effect` / `instrument`（MVP は effect のみ）
- `arch`
- `path`
- `latency_samples`（取得できれば）

### 6.2 format ごとの vendor 取得

ベンダー判定はプラグイン形式ごとに異なるため、バックエンドごとに metadata 取得を抽象化する。

| Format | 取得元 |
|---|---|
| CLAP | `clap_plugin_descriptor.vendor`、`id`、`name` |
| VST3 | `PFactoryInfo.vendor`、`PClassInfo2.vendor`、factory / class info |
| VST2 | `effGetVendorString`、`effGetProductString`、`effGetVendorVersion` |

`vendor_raw` はそのまま保存し、`vendor_key` は Unicode NFKC、trim、空白正規化、casefold で作る。

### 6.3 グループ解決の優先順位

1. `[[plugin_groups.rules]]` の明示ルール（先勝ち）
2. `[vendor_aliases]`
3. 正規化済み vendor 文字列
4. プラグイン ID の reverse-DNS prefix
5. プラグインの親ディレクトリ名
6. `default`

```toml
[vendor_aliases]
"fabfilter software instruments" = "fabfilter"

[[plugin_groups.rules]]
format = "clap"
id = "com.fabfilter.*"
group = "fabfilter"

[[plugin_groups.rules]]
format = "vst3"
path = "**/FabFilter/*"
group = "fabfilter"
```

- 自動判定が外れた場合は設定で上書きできる
- 同一 vendor を複数グループに分けたい場合もルールで対応する
- 異なる vendor を同一グループにまとめたい場合もルール / alias で対応する
- `group = "default"` または vendor 空の場合は警告をログに出す
- `paw catalog list` で `vendor_raw` / `vendor_key` / `group` / `group_source` を確認できるようにする

### 6.4 Worker key

MVP では `group` を Worker key とする。将来は `group + arch` にする。

## 7. 音声パスとレイテンシ

### 7.1 音声の転送

- Client は DAW の `process` 呼び出しごとに 1 ブロックを送る
- ブロックが MTU を超える場合はフラグメント化する
- ヘッダに `sample_pos`, `frames`, `fragment_index`, `fragment_count` を持たせる
- Worker はブロックを再構成し、DAW と同じブロックサイズでプラグインを process する
- 音声は UDP、planar f32
- 制御は TCP。音声と制御は独立した経路とする

### 7.2 DAW 設定への追従

ASIO バッファサイズそのものはプラグイン API から直接取得できない。CLAP の `activate(sample_rate, min_frames, max_frames)`、VST3 の `setupProcessing(maxSamplesPerBlock)` を DAW 設定の代理値として使う。

```text
daw_block_frames = max_frames_count / maxSamplesPerBlock
（取得できない場合は設定値 block_size を使う）

daw_block_ms = daw_block_frames / sample_rate * 1000
jitter_ms = max(10.0, daw_block_ms)      # auto のデフォルト
jitter_samples = ceil(jitter_ms * sample_rate / 1000)

report_latency_samples =
    jitter_samples
  + plugin_latency_samples
  + safety_samples
```

- **DAW 自身の ASIO バッファをプラグイン遅延に加算しない**。PDC が二重補正になる
- DAW のブロックサイズはジッター量の基準として使う
- DAW のブロックが小さい場合にジッターが不足しないよう、最低 10ms を持たせる
- DAW のブロックサイズ / サンプルレートが変わったら再 activate が来るので再計算する
- Host のプラグイン遅延がロード後に判明したら `request_restart` で報告値を更新する
- 起動完了前は `plugin_latency_samples = 0` として暫定値を報告する

```toml
[audio]
latency_policy = "follow_daw"   # follow_daw | fixed
jitter_ms = "auto"              # auto | number
jitter_blocks = "auto"          # auto | number
block_size = 256                # フォールバック
safety_samples = 0
```

### 7.3 ジッタバッファ

- Client は `jitter_samples` を目標に出力を遅延させる
- 欠落パケットはフェード付き無音で補間する
- アンダーラン / レイトパケットは統計に記録する
- RTT は ping / pong で計測するが、PDC には設定したジッター値を使う

## 8. 制御プロトコル

### 8.1 レイヤ

| レイヤ | MVP | 将来 |
|---|---|---|
| Transport | TCP（control）、UDP（audio） | QUIC |
| Framing | 長さ付きフレーム | 同じ |
| Codec | CBOR (`ciborium`) | CBOR + Protobuf |
| RPC | request / response / event | 同じ |

制御と音声は独立している。音声を CBOR / Protobuf に載せない。

### 8.2 codec の選定

比較した方式:

- JSON / JSON-RPC: 可読性は高いが、state が大きいと base64 で膨らむ
- MessagePack: バイナリネイティブで手軽だが、自己記述性は低い
- CBOR: バイナリネイティブで標準化されており、diagnostic notation でデバッグできる
- Protocol Buffers: スキーマと互換性に強いが、MVP では IDL / codegen のコストが重い
- bincode / postcard: 高速だが自己記述ではなく、Client / Host のバージョンずれに弱い
- gRPC: 制御 API には過剰
- OSC: セッション管理 / state 転送には不向き

**MVP は CBOR、最終的には Protobuf へ移行する**。フレーミングとメッセージ意味論を codec 非依存にし、`hello` で codec を交渉する。

### 8.3 codec 非依存のルール

- bool / 整数 / 浮動小数 / 文字列 / bytes / 配列 / map / optional に限定する
- CBOR 固有の tag、indefinite length、非文字列キーは使わない
- enum は明示的な文字列タグ、または整数 enum にする
- 未知フィールドは無視する
- 追加フィールドは optional / default にする
- `Value` のような動的型をメッセージに使わない

### 8.4 フレーミング

```text
u32 payload_len
u8  frame_type
u8  flags
u16 reserved
u64 request_id
payload
```

- 最大 control frame は 16 MiB
- state はチャンクに分ける

### 8.5 state proxy

- Client の `save` で Host のプラグイン state を取得し、DAW プロジェクトに埋め込む
- Client の `load` で Host のセッション作成後に state を送る
- state はチャンク転送する
- 保存時に Host が応答しない場合は、Client が保持する直近のキャッシュを保存する
- Host にプラグインが無い場合は state を保持したまま無音 + エラー表示にする

state envelope:

```text
magic "PAWS1" | version | format | plugin_id | host_version | payload
```

### 8.6 再接続

- control 接続が切れた場合はセッションを猶予付きで保持する
- Worker が落ちた場合は `session.lost` を Client に通知する
- Client は指数バックオフで再接続し、state を復元する
- 再起動ループを避けるため、連続失敗回数に上限を設ける

## 9. セキュリティ

- Supervisor / Worker はデフォルトで `127.0.0.1` に bind する
- endpoint ファイルはユーザー権限 0700 のディレクトリに置く
- `hello` で token を検証する
- Worker の control 接続にも別 token を使う
- 音声パケットには `session_token` を含め、Worker が検証する
- Client はプラグインのパスを送れない。カタログ ID + allowlist のみ
- 将来のリモート LAN 利用時は bind アドレスと firewall 設定を明示する

## 10. テスト方針

### 10.1 テスト用プラグイン

以下を Linux / Windows の両方にビルドする。

- `paw.test.gain`: 音声パス確認用
- `paw.test.latency`: 既知の遅延（例 128 samples）を報告
- `paw.test.state`: state save/load 確認用
- `paw.test.same_a` / `paw.test.same_b`: 同一 vendor。共通 DLL / SO のグローバル変数で同一プロセス判定
- `paw.test.other`: 別 vendor。別 Worker になることの確認
- `paw.test.crash`: 任意のタイミングで abort し、Worker 分離を確認

同一 vendor のテストには、両プラグインがリンクする共通ライブラリを使う。同一 Worker なら共通ライブラリのグローバルを共有し、別 Worker なら共有しない。

### 10.2 テスト項目

- 音声の sine パススルー
- ジッター / パケットロス / アンダーラン
- state save/load
- レイテンシ報告
- 同一 vendor が同一 Worker に入ること
- 別 vendor が別 Worker に入ること
- Worker クラッシュ時に他 vendor のセッションが継続すること
- Wine prefix の自動起動 / endpoint / 再接続
- 32-bit は MVP 後

## 11. ロードマップ

1. **Linux DAW + Linux native Host**
   - CLAP / エフェクトのみ
   - Supervisor + vendor worker
   - UDP 音声、ジッタ、state proxy、レイテンシ報告
   - vendor 分離 / 同一 vendor IPC の検証
   - CLI / テストプラグイン
2. **Linux DAW + Wine Host**
   - `pawd.exe` を `x86_64-pc-windows-gnu` でビルド
   - Wine prefix の自動起動、endpoint、worker spawn
   - Windows CLAP / テストプラグイン
3. **Windows DAW**
   - VST3 Client
   - VST3 Host backend
   - 可能なら VST2 Host backend
   - native Windows Host
   - Windows DAW の音声設定への追従

macOS / AU は開発用ハードウェアが無いため、現時点の対象外。Phase 4 は設けない。Runtime 抽象とプラグイン形式の抽象化は残し、将来環境が用意できた段階で追加できるようにする。

### 12.1 GUI streaming

MVP では実装しないが、アーキテクチャ上は Host の GUI extension と Client の editor を追加できるようにしておく。

```toml
[gui]
mode = "none"        # none | host_window | stream
```

- `none`: GUI なし
- `host_window`: Host 側のディスプレイにプラグイン GUI を表示する
  - 同一マシンで Wine prefix 間ブリッジする場合など
  - GUI streaming は off
- `stream`: プラグインウィンドウをキャプチャして Client に配信する
  - LAN 経由で別マシンの Host を使う場合
  - マウス / キーボード入力を Host に転送する

実装上の検討事項:

- キャプチャ
  - Windows: Windows Graphics Capture / DWM / PrintWindow
  - Wine: X11 (XComposite など)
  - Linux native: X11 / Wayland (PipeWire)
- エンコード: H.264 / VP9 / AV1、低遅延優先。必要なら JPEG / zstd の簡易モード
- 入力転送: 座標変換、フォーカス、修飾キー、ホイール、セキュリティ / 誤操作対策
- Client 側: CLAP GUI / VST3 editor に映像サーフェスを埋め込む
- 転送: 音声 / 制御とは別の TCP / QUIC ストリーム
- `hello` の capability で GUI streaming の有無を通知する

## 13. 既知の制約（許容するもの）

Wine の制約を理解しているユーザー向けの機能であるため、以下は設計上許容する。

- iLok / ドングル / カーネルドライバ依存のプラグインは動作しない可能性が高い
- COM / デスクトップ環境を要求するプラグインは、ヘッドレス環境で失敗する可能性がある
- GUI 前提のプラグインは、パラメータ proxy / GUI streaming 実装まで操作できない
- GPU アクセラレーションを前提とする GUI は、Wine の環境によって表示 / キャプチャに失敗する可能性がある
- 32-bit プラグインは MVP の対象外
- DAW のサンドボックス設定によっては、プラグインからの Host プロセス起動が制限される
- Wine prefix をまたぐプラグイン間 IPC は共有されない
- 同一 Worker 内の 1 プラグインのクラッシュで、その Worker の全セッションが失われる
- ASIO バッファサイズそのものはプラグイン API から直接取得できない
- ネットワークジッターが設定値を超えるとアンダーラン / 無音になる
- オフラインレンダリングは MVP 非対応
- 商用プラグインのバイナリ転送 / 共有は EULA 違反になり得る。本プロジェクトはバイナリ配布機能を持たない

## 14. 未決事項

- VST3 SDK のライセンスとプロジェクト全体のライセンス
- VST2 SDK の配布条件（clean-room header などの選択肢）
- GUI streaming のキャプチャ方式（Windows Graphics Capture / Wine X11 / Wayland）
- Windows Client で VST2 クライアントまで必要か
- Worker の再起動ポリシー（自動再作成の上限、state 復元のタイミング）
- Client の複数インスタンスで、インスタンスごとに異なるプラグインを選ぶ場合の設定 / state の扱い
- 可変ブロックサイズを扱う DAW への対応範囲

## 15. 結果

- 実装の出発点を Linux native + CLAP + エフェクトに絞りつつ、VST3 / VST2 / Windows / GUI streaming を後から追加できる抽象化を維持する
- ベンダーごとの Worker 分離により、プラグイン間 IPC とクラッシュ分離を両立する
- 音声は Client ↔ Worker 直結、制御は Supervisor 経由とし、レイテンシと実装の分離を両立する
- CBOR で MVP を開始し、codec 非依存の設計で Protobuf へ移行可能にする
- macOS / AU は現時点の対象外とし、ロードマップから削除する
